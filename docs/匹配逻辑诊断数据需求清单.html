01 · Delivery Brief

一页交付摘要

第一轮最小可用交付是：现行匹配代码 + 连续 7 至 14 天原始数据 + 同批次系统输出 + 中间匹配证据 + 50 至 100 个人工核验案例。只给错例或只给清洗后的结果，都无法判断问题出在输入、聚类、候选生成、评分还是最终关联。

7 至 14 天首批连续业务日期
50 至 100人工正确答案案例
5 至 20每类问题的正常对照

交付优先级

级别必须提供缺失影响
必须生产代码、有效配置、航班计划、算法节点、当前匹配结果、人工正确答案无法完整复现或判断修复是否正确
强烈建议A-CDM、运行日志、候选评分、飞机注册号、外观识别、数据库查询可定位错误，但解释能力和歧义消除受限
可选相关截图、视频时间索引、OCR 原图、历史版本结果不阻断首轮，但影响证据复核和长期回归
最重要的组合
同一节点必须能够沿着“原始行 → 当前保障组 → 候选航班 → 当前结论 → 人工正确答案”完整追踪。任何一步缺少稳定关联键，诊断都会退化为人工猜测。
02 · Code & Runtime

源码、配置与运行环境

代码包必须能在隔离环境复现同一批数据的当前结果。不要只截取一个匹配函数，因为实际行为通常还受 SQL、字段清洗、定时任务、缓存和配置覆盖影响。

项目级别交付内容验收
完整源码必须入口、匹配服务、数据访问、SQL、任务调度、工具类和测试可定位实际调用链
版本标识必须Git commit、分支、构建时间、生产发布时间代码与数据日期一致
运行配置必须时间阈值、权重、机位映射、事件映射、开关；密钥可脱敏说明默认值和生产覆盖值
依赖环境必须requirements、pom、package lock、JDK/Python/数据库版本或容器文件可独立安装
数据库结构强烈建议相关表 DDL、索引、字段注释、视图与实际查询 SQL关联键和时间字段可解释
运行说明必须导入、执行、导出命令及预期输出位置一条最小样本可跑通

不得包含

生产密码、Token、私钥、真实人员身份信息和不必要的网络地址。脱敏不得改变航班号、机位、时间相对关系、飞机注册号相似性或主外键，否则会破坏诊断价值。

03 · Package Contract

数据包结构与通用约定

建议一个压缩包对应一个代码版本和一个连续时间段。文件名、校验值和说明文件共同确定可复现边界。

matching_review_package/
├── README.md
├── manifest.json
├── code/
├── config/
├── schema/
├── input/
│   ├── flight_plans.xlsx
│   ├── algorithm_nodes.xlsx
│   ├── acdm_manual_nodes.xlsx
│   └── appearance_features.xlsx
├── current_output/

│   ├── candidates.xlsx
│   ├── node_assignments.xlsx
│   └── runtime_logs/
└── ground_truth/
    └── reviewed_cases.xlsx

README 必须说明

  • 机场、时区、数据起止日期、业务日切分规则和跨零点规则。
  • 代码 commit、生产配置版本、数据库快照时间。
  • 每个文件的行数、主键、编码、时间格式、Sheet 名和生成方式。
  • 组合机位、远近机位、临时机位和历史改名映射。
  • 已知缺失、重复、延迟、补录和时间校准问题。

04 · Raw Inputs

原始输入字段字典

原始字段必须原样保留，同时可额外提供规范化列。不要先删掉“看起来错误”的年份、重复节点、空航班号或重叠计划，因为这些正是需要诊断的对象。

外观与 OCR

建议字段：证据 ID、事件时间、摄像机、机位、航司候选、机型候选、飞机注册号 OCR 原串、标准化串、各自置信度、图片或视频帧索引、算法版本。原始图像可选，但 OCR 文本和置信度必须成对提供。

05 · Outputs & Ground Truth

现行输出、日志与人工真值

当前系统输出是被诊断对象，不是正确答案。必须同时提供最终结果与形成该结果的中间证据，才能区分“候选没生成”“候选排序错误”和“门槛判断错误”。

保障组 flight_groups

字段级别用途
group_id / temporary_code必须组主键和可读编号
node_ids必须重建聚类与节点守恒
observed_start / end必须实际保障范围
occupancy_start / end + source强烈建议占位边界来源解释
assignment_status必须匹配、待确认、无航班号或异常
assigned_plan_id / flight_no必须当前系统结论
strategy_version必须绑定代码与配置
issue_tags / lineage强烈建议异常原因和拆分合并血缘

候选与评分 candidates

每个候选至少包含 group_id、plan_id、rank、total_score、机位得分、时间窗得分、节点阶段得分、链路连续得分、顺序得分、外观航司/机型/注册号得分、排除原因、是否选中和领先分差。A-CDM 航班号不提供得分，应独立提供一致、冲突、无计划或多计划等辅助结论。若现行系统没有中间评分，应提供日志或调试开关后的同批输出。

运行日志

  • 批次开始和完成时间、任务 ID、代码版本、配置摘要、输入输出行数。
  • 每个异常或未匹配组的候选生成、规则命中和排除原因。
  • 数据库、网络、解析、时间转换和重复消费错误；禁止只给 ERROR 汇总数量。

人工真值 reviewed_cases

字段级别说明
case_id必须人工案例唯一 ID
node_ids / group_id必须答案对应的精确节点集合
current_result必须现行代码当时结果
correct_flight_no / plan_id必须最终正确航班；无计划允许只填航班号
correct_status必须MATCHED、UNASSIGNED、DATA_ERROR 等
error_type必须分组、匹配、参考、外观或原始节点错误
evidence必须A-CDM、视频、机号、现场确认等依据
reviewer / reviewed_at强烈建议答案责任与时间
真值原则
人工答案必须独立于当前系统结果录入。不能把最高候选预填后直接视为“人工确认”，否则回归集只会复制现有错误。
06 · Sample Coverage

样本范围与问题覆盖

数据必须连续，不能只挑几条错例。连续时间段能保留同机位顺序、跨零点、计划延误和前后航班关系；正常对照用于防止修复一个问题后破坏原有正确结果。

首批规模

  • 连续 7 至 14 天，优先覆盖业务量高、延误多和组合机位活跃的日期。
  • 全部航班计划与全部算法节点，不预先按“是否匹配成功”过滤。
  • 人工真值 50 至 100 组；每个问题类型至少 5 个，重点类型建议 10 至 20 个。
  • 每个问题类型附 5 至 20 个已确认正常的对照案例。

问题覆盖矩阵

问题类型必须包含真值依据
同机位计划重叠 / 多候选前后计划、完整节点链、当前候选分A-CDM 或最终人工航班
计划缺失、备降、临时航班无计划但有现场航班号的组A-CDM 航班号
计划时间偏差超过 30 分钟早到、晚到、结束超计划飞机入位与推出
跨零点、异常年份、起止倒置原始日期时间和业务日规则源系统记录
组合机位父机位与 L/R 同时段数据机位占用事实
同航班号跨机位 / 换飞机两架飞机、两个机位、三段航班关系飞机注册号 + A-CDM
同一飞机连续航班进港 A、出港 B 及过站节点航班计划与现场确认
节点开始或结束缺失只有前半段、后半段或中间节点视频 / 人工异常结论
低信息碎片少量极短节点组确认 DATA_ERROR
节点拆分与合并原节点集合、拆分点或合并组人工分组答案
A-CDM 轻微错序入位、上轮挡和录入时间入位作为绝对锚点
OCR 易混注册号B533/B53B/B524 类样本真实飞机注册号

禁止的样本方式

  • 只提供已经匹配成功的数据。
  • 只截取问题节点而不提供前后至少 8 小时计划与节点。
  • 用清洗后的时间覆盖原始时间。
  • 只给截图，不给机器可读记录和稳定 ID。
07 · Quality & Acceptance

数据质量、脱敏与验收

收到数据后先验证“能否忠实复现”，再开始改代码。若当前结果无法用交付代码和配置复现，必须先解决版本或数据口径差异。

完整性检查

  • □所有文件能读取，列名、Sheet、编码和时间格式与 README 一致。
  • □主键非空且可唯一定位；重复记录有明确业务含义。
  • □航班计划、算法节点、A-CDM、匹配结果和人工答案的关联键可闭环。
  • □输入节点总数等于最终所有组节点数，拆分合并后仍守恒。
  • □用交付代码、配置和数据可复现当前匹配结果。
  • □人工真值可形成固定回归断言，且不依赖当前结果预填。

时间质量

检查要求
时区统一声明 Asia/Shanghai 或逐字段带时区，禁止本地时间与 UTC 混用
精度算法节点保留到秒或毫秒；人工节点保留原录入精度
多时间字段事件发生、系统接收、人工录入不得混为一个字段
跨零点不得仅比较 HH:mm；必须使用完整日期时间

脱敏原则

  • 可删除姓名、电话、账号、密码、Token 和生产域名。
  • 航班号可做一致性映射，但同一航班在所有文件中必须映射为同一值。
  • 飞机注册号若脱敏，必须保持 OCR 字符相似关系；建议不脱敏或使用稳定替换表。
  • 时间可整体平移同一固定量，但所有来源必须同步平移，且跨零点关系不变。
  • 机位号不建议脱敏；如必须脱敏，父子组合关系和相邻顺序必须保留。

文件级验证

每个文件记录 SHA-256、行数和生成脚本。压缩前后重新核对哈希；任何重新导出都生成新 package_id，不覆盖旧包。

08 · Handoff Checklist

交付勾选表

以下部分可直接转发给研发、数据平台和 A-CDM 团队。交付方逐项勾选并在备注中说明缺失原因。

A. 代码与配置

  • □完整源码与 Git commit
  • □生产实际生效配置及默认配置
  • □依赖锁文件、运行环境和启动命令
  • □相关 DDL、SQL、定时任务和缓存说明
  • □最小可运行样例及预期输出

B. 原始数据

  • □连续 7 至 14 天完整航班计划
  • □同时间段全部算法节点和原始报文
  • □A-CDM / 人工现场航班号、入位、上轮挡和释放机位时间
  • □航司、机型和飞机注册号识别结果
  • □组合机位及历史机位映射

C. 当前结果与答案

  • □当前保障组及精确 node_ids
  • □候选航班、逐项评分和排除原因
  • □节点最终航班归属和占位边界来源
  • □运行日志与异常日志
  • □50 至 100 个人工正确答案及判断依据
  • □各问题类型正常对照案例

D. 数据说明与安全

  • □README、manifest、时区和业务日规则
  • □每个文件行数、主键和 SHA-256
  • □脱敏映射说明
  • □已知缺失、延迟、重复和补录说明
  • □已删除所有密码、Token、私钥和无关个人信息
收到数据后的下一步
先在隔离环境复现公司当前结果，生成“输入质量问题、现行逻辑问题、仿真规则差异、人工真值回归”四张清单；随后逐个修复并全量重跑，直到人工错例为 0、历史正确案例无回退、节点数量守恒。
